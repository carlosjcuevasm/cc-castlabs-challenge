• Notes on development "HTTP Proxy Challenge" for Castlabs

    By Carlos Cuevas carlosjcuevasm@gmail.com

    • Stages
      • M1 - Contract and implement the core
        • Define the incoming POST request format, including how the username is provided.
        • Implement JWT generation as an independent function.
        • Include iat, jti, and payload.
        • Sign the token using HS512 and the supplied hexadecimal secret.
        • Implement an asynchronous proxy that attaches x-my-jwt and forwards the POST request.
        • Deliverable: A working HTTP proxy with the required JWT behavior.
      • M2 - Packaging and Execution
        • Create the mandatory project infrastructure:
          • Dockerfile — builds the application image.
          • docker-compose.yml — defines how to run the application using Docker Compose.
          • Makefile — provides build and run targets, with configurable HTTP_PORT.
          • README.md — explains configuration, prerequisites, building, running, and using the application.
        • Deliverable: Run the application using the documented commands.
      • M3 - Add the bonus status endpoint
        • Implement /status with:
          • Time elapsed since application startup.
          • Number of requests processed.
        • Define the counter's semantics explicitly—for example, counting requests received by the application, including those that fail upstream.
        • Deliverable: The (bonus) requested working status endpoint.
      • M4 - Add automated tests
        • Test JWT claims and signature verification.
        • Test that the proxy forwards the request with the correct JWT header.
        • Test upstream responses and relevant failure scenarios.
        • Test /status endpoint
        • Add the test Makefile target.
        • Deliverable: The (bonus) repeatable test suite.
    • Main (M1)
      • Core library
        • Library Responsibility
          FastAPI Define the HTTP endpoint and validate requests
          Uvicorn Run the asynchronous web application
          HTTPX Forward requests asynchronously
          PyJWT Create and sign JWTs
      • JWT creation
        • Secret decoding: bytes.fromhex() interprets the supplied hexadecimal string as bytes.
        • now.date() uses the UTC date because now is timezone-aware and explicitly set to UTC. That avoids dependence on the container's local timezone.

      • HTTPX Pooled connections
        • Without connection pooling:
        • 			  Request 1 → Create connection → Upstream → Close connection
			  Request 2 → Create connection → Upstream → Close connection
			  Request 3 → Create connection → Upstream → Close connection
        • With a shared HTTPX client:
        • 			  Shared HTTPX client
			          │
			          ├── Request 1 ──┐
			          ├── Request 2 ──┼── Reuse pooled connections → Upstream
			          └── Request 3 ──┘
      • Endpoint /proxy
        • Assignment only says to implement an HTTP proxy that accepts POST requests.
        • Decided to expose that functionality at POST /proxy
        • An explicit route makes the endpoint easy to discover and documents its purpose clearly
      • Asynchronous calls
        • While waiting for the upstream response, the server can work on other requests rather than blocking that execution path.
        • Endpoints are to be asynchronous functions, and so is the app lifecycle
      • App lifespan
        • 			  1. STARTUP
			     ├── Read environment variables
			     ├── Validate configuration
			     └── Create HTTPX client
			  
			           yield
			             ↓

			     └── Handle incoming requests
			  
			             ↓

			     └── Close the HTTPX client

          • 				  Uvicorn starts
				      ↓
				  FastAPI startup → lifespan enters
				      ↓
				  App handles requests for hours
				      ↓
				  Uvicorn shuts down the app
				      ↓
				  Lifespan exits → cleanup runs
        • create the HTTP client once and reuse it across requests
        • Around FastApi lifespan. Using yield. Being alive in memory and being properly cleaned up are different things. If the project/process entirely, memory is eventually reclaimed by os. Not good practice to on process termination to clean up resources properly.
      • Simplifaction of headers
        • A fully transparent HTTP proxy might preserve or handle many more headers, including redirect, caching, authentication, and connection-related headers.
        • Benefits
          • More control about which headers the upstream receives
          • Easily demonstrate that x-my-jwt was added.
          • At this stage, upstream is outsourced, so better not send forward client-specific headers or what not, that aren't appropriate upstream
          • Avoid forwarding headers that HTTP clients or proxies should manage themselves, such as Host and Content-Length
        • The assignment disregards the upstream thus dropping headers must be fine
        • Focused on the essential behavior: a small POST-forwarding service with JWT injection.
      • Using Pydantic
        • Added Pydantic model
        • Swagger understands that the endpoint accepts a JSON object with a username field and can render an editable request body.
        • The request contract becomes explicit, /docs becomes more useful, and the code communicates its expectations clearly
          • Pydantic will automatically reject malformed JSON and validate the request before the endpoint executes
          • extra="allow" means requests can include fields such as message and such in addition to username.
          • The model documents the contract without unnecessarily restricting the input.
          • Note: Pydantic validates type, the explicit check still usefull because rejects empty or whitespace-only usernames.
    • Packaging and Execution (M2)
      • Notes on Dockerfile
        • Copy dependencies first: Docker can reuse the dependency-installation layer when only application code changes.
        • python:3.11-slim: Meets the Python requirement without using the larger full image.
        • PYTHONDONTWRITEBYTECODE: Avoids writing .pyc files into the container.
        • PYTHONUNBUFFERED: Makes application logs appear promptly.
        • CMD: Starts Uvicorn and allows HTTP_PORT to override the default port.
      • Notes on docker-compose.yml
        • Compose Specification: No legacy version field.
        • Configurable port: The host and container ports use the same HTTP_PORT value.
        • Secret validation: Compose refuses to start if JWT_SECRET_HEX is missing.
        • Environment variables: Compose reads .env for interpolation and passes the required values into the container.
        • Build configuration: Compose builds the image from the project's Dockerfile.
      • Notes on Makefile
        • Included .PHONY: build run as is good practice
        • Can run either make run or specify any other port like HTTP_PORT=9000 make run
    • Status endpoint (M3)
      • time.monotonic()measures elapsed time without being affected by system clock changes. Counter increments before the request is processed, invalid requests and upstream failures count too.
      • Requests to /proxy increase request's count, /status do not
    • Tests (M4)
      • test_jwt_utils.py: verifies token generation independently of HTTP.
        • check expected claims
        • checks unique jti on each run
      • test_proxy.py: verifies the API and its interaction with the upstream.
        • Successful forwarding: the original JSON body reaches the upstream, with an x-my-jwt header.
        • Upstream response: status code, body, and content type are preserved.
        • Upstream failure: a connection error produces HTTP 502.
        • Validation: missing or blank usernames are rejected.
        • Status: verifies uptime, the initial count, counting failed requests, and that /status itself doesn't increase the counter.
      • Note: Using a test-only secret keeps the tests independent of the .env file and avoids exposing the assignment secret in test code.
      • Note: Locked versions of dependencies
        • requirements.in as the human-maintained list of direct dependencies and version constraints.
        • Used pip-tools (pip-compile) to generate requirements.txt, locking exact versions of dependencies
